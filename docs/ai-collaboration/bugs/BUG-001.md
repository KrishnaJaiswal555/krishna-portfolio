# BUG-001: Cyan milestone indicator stuck on one timeline row

- Status: Fixed (pending browser confirmation)
- Next step: Manual browser pass — TEST_CHECKLIST → "Timeline indicator —
  regression fix (BUG-001)". **Not yet performed.**

## How It Was Found
- Symptom: Krishna reported that the cyan highlight in the Journey timeline
  "was previously moving correctly when clicking different options, but now
  remains stuck at the same position."
- Reproduction: Load the page, scroll to Journey, click any row. The
  highlight does not move to the clicked row; it stays on whichever row is
  nearest the centre of the viewport.
- Expected vs actual: expected the indicator to follow the selected row;
  actually it re-pinned itself to a scroll-derived row on every animation
  frame.

## What Was Tried

| Attempt | Result (worked / didn't, why) |
|---|---|
| Assume it was a CSS positioning problem | **Wrong premise.** The indicator is a per-row `box-shadow: inset` on `.jn.is-active`, not a separately positioned bar — it has no coordinates to get wrong and cannot drift. The bug had to be in *which row carries the class*. |
| Reconstruct from memory | Rejected. `git log -S ".jn:hover"` gave a definitive answer in one command, and memory would not have identified the exact commit. |
| Look for a broken click handler | There was none to break. `git log -S "addEventListener('click'"` confirmed the rail has **never** had one; the only matches are project cards, burger and menu. |

## What Worked

### Root cause — two compounding defects, both introduced in `4f2fa6e` (Phase 6)

**1. The CSS affordance was deleted.** `d626ed5` (Phases 1–4) shipped:

```css
.jn:hover, .jn.is-active { background: var(--accent-dim); padding-left: 18px; }
```

The highlight followed the pointer through **pure CSS `:hover`** — instant, on
every row, with no JavaScript involved. That is the behaviour Krishna
remembers. Phase 6 removed `.jn:hover` from that rule, leaving the highlight
entirely dependent on the `is-active` class.

**2. The scroll branch overrode everything, every frame.** Phase 6 made
`journey.js` the sole source of `is-active`, and its frame loop ran:

```js
if (hovering < 0 && centres.length) { …; setActive(best); }
```

`pointerleave` sets `hovering = -1`, so the moment the pointer left a row the
scroll branch reclaimed control — and with a stationary viewport `best` is
constant, so the indicator returned to the same row on every frame. Visually:
frozen.

**3. Aggravating factor.** The entire active-state mechanism sat *below* the
`if (!gl) return null` guard, so on any machine without WebGL2 there was no
indicator at all — despite the highlight being pure CSS that owes the canvas
nothing.

Phase 6 also changed the rows from `<button>` to `<div>`, on the recorded
reasoning that "a control which does nothing is worse than plain text for
assistive tech". That reasoning was **correct at the time** — activating a row
genuinely did nothing. It stopped being correct the moment the rows needed to
respond to clicks, and nothing reopened the decision.

### Fix
- Indicator logic lifted **above** the WebGL guard; it now runs regardless of
  canvas availability, and a missing context returns a partial-success object
  rather than `null`.
- Added a `pinned` index. Precedence is **pin > hover > scroll**; the frame
  loop now reads `if (pinned < 0 && hovering < 0 …)`, so scroll can no longer
  undo a click.
- Click pins a row; clicking it again releases the pin, so the control is
  never a one-way trap.
- Rows are `<button type="button">` again with `aria-pressed` maintained in
  JS, so the pinned state is announced and not merely painted.
- `.jn:hover:not(.is-active)` restores a CSS hover affordance, so the rail
  still responds under the pointer even if the scene module never runs.
- Fixed an unrelated defect found while reading: `[data-reveal]` and `.jn`
  both declared `transition` at identical specificity, and `.jn` — being later
  in the file — won outright, silently killing the reveal animation on the
  rail. `.jn`'s transition list now includes `opacity` and `transform`.

### A second defect, found by executing the fix rather than reading it

The first fix passed every static check — syntax, single `setActive`, no dead
imports, `aria-pressed` contract matched between JS and CSS. A headless
behavioural test then failed immediately:

```
FAIL  row 0 reports aria-pressed="true" — got false
```

**Cause.** `setActive(i)` opened with `if (i === active …) return;`, and the
`aria-pressed` sync had been folded into the same function. But that sync
depends on `pinned`, not on `active` — two different pieces of state behind
one guard. Clicking a row that is *already active* flips `pinned` and then
hits the early return, so the pin was painted but never announced.

This is not an edge case. Row 0 is active on load, and **hover makes a row
active** — so hovering then clicking, which is what every mouse user does,
failed to update `aria-pressed` on every row.

**Fix.** `syncPinned()` extracted and called from the click handler, where
`pinned` actually changes, plus once at init. `setActive()`'s guard now
protects only the concern it is about.

### Automated interaction test

`node tools/journey-interaction.mjs` drives the real `initJourney()` against a
DOM stub whose `getContext()` returns **null** — forcing the no-WebGL branch,
which is precisely the path that used to bail before wiring any listeners. It
then fires real click / pointerenter / pointerleave events.

It lives in `tools/`, not in a scratch directory. It found a defect that every
static check passed clean, so it is a project asset, and a pointer to a
session-scoped temp path would be dead the moment the session ended.
