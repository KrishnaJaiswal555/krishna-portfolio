# BUG-003: The site backdrop is static on desktop

- Status: Fixed, awaiting browser confirmation
- Next step: Krishna scrolls the deployed site on a desktop browser and on
  iOS, and reports whether the motion reads as subtle rather than distracting.

## How it was found

Reported by Krishna against the deployed site: on mobile Safari the cinematic
background visibly moves while scrolling; on desktop it appears almost
completely static.

## Root cause

**There was no parallax system.** `body::before` in `app.css` is
`position: fixed; inset: 0` with no transform and no scroll binding of any
kind. `position: fixed` pins a layer to the viewport, so on desktop it was
exactly, correctly immobile. Nothing was broken, disabled or misconfigured —
the feature had never been built.

The report's framing is what made this worth writing down. "Mobile works,
desktop doesn't" presents as a platform bug and invites a search for the
desktop-specific thing that is switched off. There is no such thing, because:

**The mobile motion is not the feature either.** It is an iOS Safari artifact.
Safari collapses and expands the URL bar during a scroll, which changes the
visual viewport height; a `position: fixed; inset: 0` layer painted with
`background-size: cover` is re-laid-out and re-centred as that happens, so the
artwork shifts. It is a side effect of viewport chrome, it is not scroll-linked
in any controllable way, and it has no desktop equivalent to enable.

So the correct reading was not "desktop is broken" but **"neither platform has
this feature; one of them has a coincidence that resembles it."**

## What was checked before concluding

Krishna asked specifically whether an existing system was merely inert on
desktop. It was not, and the check was worth making — the codebase does have
several scroll-driven systems, none of which touch the backdrop:

| Location | Scroll-driven? | Moves the backdrop? |
|---|---|---|
| `scenes/about.js` → `offset:` from `sp` | yes | no — particles inside `#aboutStage` |
| `scenes/journey.js` → focus tracking, alpha from `sp` | yes | no — particles inside `#journeyStage` |
| `scenes/universe.js` → entrance, depth parallax | yes | no — the project cards |
| `main.js` → `is-scrolled` | yes | no — header visibility only |
| `styles/app.css` → `body::before` | **no** | **this is the backdrop** |
| `styles/scenes.css` → `.universe::before` | n/a | deleted 2026-09-22, must not return |

Every existing scroll effect is a per-section WebGL canvas. None of them could
be reused for a page-level backdrop, and none of them was disabled.

## The fix

`src/lib/backdrop.js` — a small module that publishes a damped, scroll-linked
offset as a CSS custom property, which `body::before` consumes.

Decisions worth keeping (full rationale in DECISIONS.md):

- **A custom property, not inline style.** The target is a pseudo-element, and
  JS cannot set inline styles on `::before`. Custom properties set on `<html>`
  inherit into it.
- **`transform`, not `background-position`.** Composites on the GPU, no repaint
  of a 226 KB image, and it stays off the main thread. Krishna explicitly asked
  that it not feel like a background-position step.
- **Damped, not assigned.** `damp()` from `lib/ease.js` — the existing helper,
  reused rather than reinvented — so the motion is continuous and eased, and
  frame-rate independent between 60Hz and 144Hz.
- **`inset: -7vh 0` on the layer.** Vertical slack so the translate can never
  pull an uncovered edge into view. Peak measured offset is 44.98px against
  63px of slack.
- **Coarse pointers get 4.5% of viewport height; mice get 10%.** The iOS
  artifact above is still happening on touch devices and the two compose, so
  matching desktop's amplitude there would overshoot behaviour Krishna reported
  as already correct.
- **`scrollHeight` is cached and re-measured on resize, never per frame.** It
  forces a layout calculation; reading it every frame during a scroll is the
  forced synchronous reflow this had to avoid.
- **The rAF loop stops when the value settles** and restarts on scroll. A
  permanently running frame loop is the main battery cost of an effect like
  this, and it would have been the project's only unbounded one.

## Verification

### Automated — `node tools/backdrop-motion.mjs`, run 2026-09-23, all green

A new headless harness, written because this defect is invisible to every
other check: a static backdrop produces no error, no warning and no broken
layout. Only measuring the offset at two scroll positions distinguishes
"parallax working" from "parallax absent" — which is the exact distinction
that was wrong.

| Assertion | Result |
|---|---|
| reduced motion → returns null, requests no frame, writes nothing | ✅ |
| an offset is published at top and at bottom of the page | ✅ |
| **the backdrop moved between them** | ✅ 89.96px |
| it moves upward as the page descends, centred on zero | ✅ +44.98 → −44.98 |
| peak offset stays inside the CSS slack | ✅ 44.98px < 63px |
| one frame does not land on the final value (eased, not stepped) | ✅ |
| the rAF loop stops once settled, and a scroll restarts it | ✅ |
| coarse pointer moves less than a mouse | ✅ 40.5px vs 89.96px |

### Manual — NOT performed

No browser pass has been done. These checks prove the offset is computed,
bounded and eased; they cannot tell you whether the artwork looks right, and
must not be recorded as having done so.
