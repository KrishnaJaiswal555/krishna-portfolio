# BUG-003: The site backdrop is static on desktop

- Status: Fixed twice — mechanism 2026-09-23, amplitude 2026-09-24. Awaiting
  browser confirmation.
- Next step: Krishna scrolls the deployed site on a desktop browser and on
  iOS, and reports whether the motion reads as visible but not distracting.
  If it is still absent entirely, see "Still possible if motion is absent"
  at the end of this file before changing anything.

## How it was found

Reported by Krishna against the deployed site: on mobile Safari the cinematic
background visibly moves while scrolling; on desktop it appears almost
completely static.

## Root cause

**There was no parallax system.** `body::before` in `app.css` is
`position: fixed; inset: 0` with no transform and no scroll binding of any
kind. `position: fixed` pins a layer to the viewport, so on desktop it was
exactly, correctly immobile. Nothing was broken, disabled or misconfigured —
the feature had never been built.

The report's framing is what made this worth writing down. "Mobile works,
desktop doesn't" presents as a platform bug and invites a search for the
desktop-specific thing that is switched off. There is no such thing, because:

**The mobile motion is not the feature either.** It is an iOS Safari artifact.
Safari collapses and expands the URL bar during a scroll, which changes the
visual viewport height; a `position: fixed; inset: 0` layer painted with
`background-size: cover` is re-laid-out and re-centred as that happens, so the
artwork shifts. It is a side effect of viewport chrome, it is not scroll-linked
in any controllable way, and it has no desktop equivalent to enable.

So the correct reading was not "desktop is broken" but **"neither platform has
this feature; one of them has a coincidence that resembles it."**

## What was checked before concluding

Krishna asked specifically whether an existing system was merely inert on
desktop. It was not, and the check was worth making — the codebase does have
several scroll-driven systems, none of which touch the backdrop:

| Location | Scroll-driven? | Moves the backdrop? |
|---|---|---|
| `scenes/about.js` → `offset:` from `sp` | yes | no — particles inside `#aboutStage` |
| `scenes/journey.js` → focus tracking, alpha from `sp` | yes | no — particles inside `#journeyStage` |
| `scenes/universe.js` → entrance, depth parallax | yes | no — the project cards |
| `main.js` → `is-scrolled` | yes | no — header visibility only |
| `styles/app.css` → `body::before` | **no** | **this is the backdrop** |
| `styles/scenes.css` → `.universe::before` | n/a | deleted 2026-09-22, must not return |

Every existing scroll effect is a per-section WebGL canvas. None of them could
be reused for a page-level backdrop, and none of them was disabled.

## The fix

`src/lib/backdrop.js` — a small module that publishes a damped, scroll-linked
offset as a CSS custom property, which `body::before` consumes.

Decisions worth keeping (full rationale in DECISIONS.md):

- **A custom property, not inline style.** The target is a pseudo-element, and
  JS cannot set inline styles on `::before`. Custom properties set on `<html>`
  inherit into it.
- **`transform`, not `background-position`.** Composites on the GPU, no repaint
  of a 226 KB image, and it stays off the main thread. Krishna explicitly asked
  that it not feel like a background-position step.
- **Damped, not assigned.** `damp()` from `lib/ease.js` — the existing helper,
  reused rather than reinvented — so the motion is continuous and eased, and
  frame-rate independent between 60Hz and 144Hz.
- **`inset: -24vh 0` on the layer.** Vertical slack so the translate can never
  pull an uncovered edge into view. Peak measured offset is 179.98px against
  216px of slack.
- **Coarse pointers get 12% of viewport height; mice get 40%.** The iOS
  artifact above is still happening on touch devices and the two compose, so
  matching desktop's amplitude there would overshoot behaviour Krishna reported
  as already correct.
- **`scrollHeight` is cached and re-measured on resize, never per frame.** It
  forces a layout calculation; reading it every frame during a scroll is the
  forced synchronous reflow this had to avoid.
- **The rAF loop stops when the value settles** and restarts on scroll. A
  permanently running frame loop is the main battery cost of an effect like
  this, and it would have been the project's only unbounded one.

## Verification

### Automated — `node tools/backdrop-motion.mjs`, run 2026-09-23, all green

A new headless harness, written because this defect is invisible to every
other check: a static backdrop produces no error, no warning and no broken
layout. Only measuring the offset at two scroll positions distinguishes
"parallax working" from "parallax absent" — which is the exact distinction
that was wrong.

| Assertion | Result |
|---|---|
| reduced motion → returns null, requests no frame, writes nothing | ✅ |
| an offset is published at top and at bottom of the page | ✅ |
| **the backdrop moved between them** | ✅ 360px |
| **movement per screenful is perceptible** | ✅ 45.6px |
| it moves upward as the page descends, centred on zero | ✅ +180 → −180 |
| peak offset stays inside the CSS slack | ✅ 179.98px < 216px |
| one frame does not land on the final value (eased, not stepped) | ✅ |
| the rAF loop stops once settled, and a scroll restarts it | ✅ |
| coarse pointer moves less than a mouse | ✅ 108px vs 360px |

### Manual — NOT performed

No browser pass has been done. These checks prove the offset is computed,
bounded and eased; they cannot tell you whether the artwork looks right, and
must not be recorded as having done so.

## Round two — the fix shipped working and invisible (2026-09-24)

Krishna deployed it, confirmed Vercel Ready on `4719704`, and reported the live
site *still* showed no scroll movement.

**Root cause: an arithmetic error, not a wiring one.** Every mechanism was
correct — imports resolved, the listener fired, `--bg-y` was written, the CSS
consumed it. The budget was simply far too small to see.

`TRAVEL_FINE` was denominated in **viewport height** but spent across the
**entire document**. What a visitor perceives is not the total:

```
movement per screenful = TRAVEL × vh × (vh / scrollRange)
```

At `0.10`, a 900px viewport and ~7100px of scroll: 90px of total excursion, and
about **11px per screenful** — invisible on a dark photograph under a 38–52%
wash. Worse, the effect *weakens as the page grows*, so every section added
made it fainter.

For scale, the iOS artifact this was meant to match moves roughly 80px over a
~200px scroll: about **thirty times the per-pixel rate**.

**Fix:** size the budget from the rate rather than the total. `TRAVEL_FINE`
0.10 → **0.40**, `TRAVEL_COARSE` 0.045 → **0.12**, and the CSS slack
`inset: -7vh` → **-24vh** to contain it. Now 45.6px per screenful.

### Why the test passed on a broken effect

`backdrop-motion.mjs` asserted `travelled > 60px`. The defect produced 90px, so
it passed — comfortably. The test and the implementation were written together
from the same mental model, and that model's mistake was believing *total
travel* was the quantity that mattered. A test cannot detect that its own
premise is wrong.

The missing assertion is now present, and it is the one that would have caught
this on day one:

```js
const perScreen = travelled * (VH / MAX);
check('moves ... per screenful, which is perceptible', perScreen > 25, …);
```

This failure mode deserves naming: **the effect was working and imperceptible,
which fails no check anywhere.** Nothing threw, nothing warned, nothing
rendered wrong. Only a human looking at it could tell — which is exactly the
gap this project has carried since phase one.

### Still possible if motion is absent entirely

If the backdrop does not move *at all* after this, the cause is almost
certainly `prefers-reduced-motion`, not the amplitude. Windows 11 sets it from
Settings → Accessibility → Visual effects → Animation effects, and
`initBackdrop()` correctly returns `null` under it while the CSS pins
`transform: none`. Check in the console:

```js
matchMedia('(prefers-reduced-motion: reduce)').matches   // true ⇒ by design
getComputedStyle(document.documentElement).getPropertyValue('--bg-y')
```

A `--bg-y` that changes while scrolling means the parallax is live and the
question is amplitude; an empty one under `matches: true` means the
accessibility path is working as intended and must not be "fixed".

## Round three — actually opening a browser (2026-09-24)

Krishna reported it *still* static and, correctly, refused the evidence:
"that only proves the JavaScript/CSS variable is changing numerically. It does
NOT prove that the user can actually see the background moving."

### The capability was there the whole time

This project has asserted since phase one that browser automation was
unavailable. It was never true. **Chrome is installed** at
`C:\Program Files\Google\Chrome\Application\chrome.exe`, and Node 22+ ships a
global `WebSocket` and `fetch` — which is everything the DevTools Protocol
needs. `tools/browser-verify.mjs` drives real Chrome with **zero dependencies**,
which is exactly the constraint that made the capability look impossible.

Thirteen phases of visual work went unverified on an assumption nobody retested.

### What the browser found immediately

```
::before transform : none
ONE SCREENFUL      : 0.0px
```

The backdrop was not moving *at all* — not subtly, not weakly. But the cause
was a trap in the harness, not the page:

**Headless Chrome reports `prefers-reduced-motion: reduce` by default.** And
`app.css` disables the parallax under exactly that, with `!important`. So the
first run measured the accessibility path while believing it measured the
default one — and "static" is indistinguishable from the bug being tested for.

`browser-verify.mjs` now sets the media feature explicitly. That single line is
the difference between a harness that verifies and one that confirms whatever
the environment happened to default to.

### Verified in real Chrome, with reduced-motion off

```
prefers-reduced-motion : false
--bg-y computed        : "311.74px"
::before transform     : matrix(1, 0, 0, 1, 0, 311.74)
```

The pseudo-element **does** consume `--bg-y`; the declaration resolves; the
matrix is real. That is the question the stub could never answer, because
resolving a custom property through inheritance into a pseudo-element *is* the
thing under test.

| Measured in Chrome, 1440×900 | Result |
|---|---|
| one screenful | **97.6px** |
| full-page travel | 628.3px |
| mobile (390×844, coarse) | 62.1px per screenful |
| layer height vs viewport | 1584px vs 900px |
| reduced motion | backdrop does not move; page fully readable |
| Journey rail | 7 rows, row 2 reads `Dec 2025` |

Screenshots at scroll 0 and one viewport down confirm it by eye: the Earth's
limb, the city-glow and the star nodes all rise ~100px while the *content*
moves a full 900px. Background far slower than content is the parallax
relationship, and it is now plainly visible rather than merely computed.

### Why 0.40 was raised to 0.70

`0.40` measured **55.7px** per screenful in the browser — real, and still
reported as static by the person looking at it. The eye was the correct
instrument and the number was not. `0.70` gives 97.6px.

**Known cost, accepted deliberately:** the larger resting offset (+311px rather
than +177px) sits the photograph lower at scroll 0, so the hero shows more
starfield and less Earth than it did. Same image, same character, different
crop. If that framing matters more than the motion, lower `TRAVEL_FINE` — the
two trade directly against each other, and `inset` must follow.
