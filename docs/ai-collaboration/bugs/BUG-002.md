# BUG-002: Project card artwork never painted — detached lazy image deadlock

- Status: Fixed (pending browser confirmation)
- Next step: Open `/tools/debug-art.html` and the Work section. **Not yet
  confirmed in a browser.**

## How It Was Found
- Symptom: Krishna reported that after the artwork was integrated, the Work
  section rendered titles, descriptions, tags, buttons and cyan hover
  correctly — but the artwork area on every card was "completely dark/empty".
- Reproduction: load the site, scroll to Work. Every `.pc__art` shows only its
  `--bg-2` background under the overlay.
- Expected vs actual: expected each card's photograph; actually nothing was
  ever inserted into the container.

### The decisive clue
**The background image rendered fine.** That is a CSS `url()`; the card
artwork goes through JavaScript. So the file, the path and the MIME type were
all provably fine — HTTP returned `200 image/jpeg` with matching byte counts —
and the fault had to be downstream of the network.

The second clue was the *absence* of evidence: no console error, no failed
request, and **not even the generated schematic**, which should have appeared
if loading had failed. Something that neither succeeds nor fails.

## What Was Tried

| Attempt | Result |
|---|---|
| Re-verify the asset paths over HTTP | Already green, and re-confirmed green. This is what made it clear the bug was not in the asset layer — and that all prior verification had been testing the wrong layer. |
| Suspect the `.pc__art::after` overlay | Plausible but wrong. It is translucent (`.12` → `.72` gradient), so it would dim the artwork, never erase it. |
| Suspect `universe.js` writing `opacity` per frame | Ruled out by Krishna's own report: the card *body* was fully visible, so the card was not transparent. |
| Suspect the container collapsing to zero height | Ruled out: `.pc__art` has `aspect-ratio: 3/2`, and Krishna reported the space was reserved. |
| **Read `art()` and find a detached image marked lazy** | **Root cause.** |

## What Worked

### Root cause
`assets.js → art()` created a **detached** `new Image()` and set
`img.loading = 'lazy'` before assigning `src`:

```js
const img = new Image();
img.loading = 'lazy';          // <- the bug
img.onload  = () => resolve(img);
img.onerror = () => { i += 1; tryNext(); };
img.src = list[i];
```

Lazy loading is defined for images **connected to a document**. This image is
detached — it is only appended once it resolves — so the lazy hint can defer
the fetch indefinitely. Neither `onload` nor `onerror` ever fires, so:

1. the promise never settles,
2. `artWrap.append(node)` in `main.js` never runs,
3. the frame stays empty showing only its background,
4. **nothing is logged**, because nothing failed. It simply never finished.

A circular wait: the image will not load until it is in the document, and it
is not put in the document until it loads.

This also explains the complaint that predated the assets entirely. The
generated schematic was never appearing either — the "large empty dark areas"
reported before any image existed were this same deadlock, not a design
problem with the schematic.

### Fix
- Removed the lazy hint from the detached image. (Lazy loading on a *rendered*
  `<img>` would be fine; it is the detached-plus-lazy combination that
  deadlocks.)
- Added a **stall guard**: each attempt is raced against `STALL_MS`, so the
  promise always settles regardless of what the image does, and logs a warning
  naming the path that hung. A deadlock that produces silence is worse than
  one that throws.
- Tightened the exhausted branch to set `settled` before resolving — it was
  the one exit path bypassing the helper that exists to centralise settling.
- `scenes.css`: explicit `position: relative; z-index: 0` on the artwork image,
  so its order against `.pc__art::after` is stated rather than incidental.
  `universe.js` writes a transform to every card each frame and the deck sets
  `transform-style: preserve-3d`; both create stacking contexts, and that
  interaction should not be something the layout depends on implicitly.

## Verification

### `tools/art-loader.mjs` — new, and the test that was missing
Nothing had ever tested the loader; `art-smoke.mjs` covers only
`placeholder()`. The new harness stubs `Image` and asserts one absolute
property: **`art()` always settles.**

| Case | Result |
|---|---|
| First candidate loads → resolves with that image | ✅ |
| First errors → falls through to the second candidate | ✅ (proves the retry chain survived the rewrite, i.e. `settled` is scoped per-promise, not per-attempt) |
| All candidates error → resolves with the schematic, warns once | ✅ |
| **Image neither loads nor errors → still settles** | ✅ at 8010ms, with the schematic and a "neither loaded nor failed" warning |

### Regression
19/19 modules parse · `14 checks passed` · journey-interaction, art-smoke and
deploy-audit all green · stylesheet braces balanced · served `assets.js` shows
`img.loading` **0 times** and the tightened branch present.

### What this does NOT prove
The lazy hint and the stall guard were changed together, so the test proves
the contract holds — not that the hint was the sole cause. If some other
mechanism stalls the load in a real browser, the guard now converts it from
"empty forever, silently" into "schematic after 8s, with a named warning":
diagnosable rather than invisible.

**Browser confirmation is still required**, and is the only thing that can
close this. `/tools/debug-art.html` reports, per project, whether the promise
settled, what it resolved with, the resolved `src`, and computed styles — with
a control row that loads the same files via a plain `<img>`, so the loader and
the file can be told apart.
